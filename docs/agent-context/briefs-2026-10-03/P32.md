# Task P32: FIX THE FARMING TARGETS FREEZE (errors report item 67): the place index is O(n squared) in string normalisation and WebKit's toLocaleLowerCase is extremely slow

## PROVEN cause (stack samples of the frozen app, 2026-10-04 12:52, build 12:50)
The WebKit web process main thread sat at 100% CPU for minutes. `gdb` stack samples (5) of the main thread: three in `JSC::stringProtoFuncToLocaleLowerCase` (inside `JSC::defaultLocale` -> `canonicalizeUnicodeLocaleID` -> ICU `uloc_forLanguageTag`/`uloc_canonicalize`, and `String::utf8`), one in `String.prototype.replaceAll`, one in a regexp `String.prototype.replace`. In WebKitGTK's JavaScriptCore `toLocaleLowerCase()` re-parses the default locale on EVERY call, so it is roughly two orders of magnitude slower than in Node (V8); our timing in Node (0.5 s for the place index) therefore hid the problem. Code that does it: `const lower = (value) => String(value ?? '').trim().toLocaleLowerCase()` and `vendorKey = lower(...).replaceAll('’', "'").replace(/\s+/g, ' ')` in src/lib/farmingTargets/screenModel.js (lines ~9-10), the same `lower` in farmNext.js, placeIndex.js, relicPlaces.js, plus `toLocaleLowerCase` in groupRankedByPlanet.js. The freeze appeared with job P27 (build 22:48), which added code to `buildPreviewPlaceIndex` (screenModel.js) that does a full scan with a normalisation per element: (a) `itemNameForKey` (~line 276-281): `[...exportNames.values()].find((name) => vendorKey(name) === key)` runs for every Market/override row and normalises EVERY export name (tens of thousands) each time; (b) `canonicalVendorName` (~line 51-72) normalises all ~107 wiki vendor names several times per call and is called for every wiki vendor row (~2,500) and every DE vendor offer (~1,900). That is hundreds of millions of normalisations in JavaScriptCore.
