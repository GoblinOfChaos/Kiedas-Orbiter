## What this does and does not cover

There are two distinct ways an item can end up with no picture on screen:

- **(a) No URL is known for the item at all.** Every map in the pipeline
  (`EI`, `nameToImage`, the export tables' own `icon`/`texture` fields, the
  warframe-items thumbnails) comes back empty, so the resolver returns `null`
  and the card renders with no `<img>` at all. **This is the only failure mode
  inventoried below** — it is a data gap that is visible statically.
- **(b) A URL is known but 404s when loaded.** The resolver returns a URL, the
  card renders an `<img>`, and the fetch fails at runtime (stale wiki thumbnail
  name, asset never mirrored, cache miss). **This audit cannot see those** — it
  never performs a network request. An item absent from this report may still
  show a broken image in the app.

The "URL known elsewhere?" column in each table separates two sub-cases of (a):
a `yes` means `resolveAnyImage()` (which consults `EI`/`nameToImage`) does find a
URL for the item and only the screen's own resolution path misses it — a code
gap, not a missing asset. A `no` means nothing in the pipeline knows a URL.

## Data sources used

The DE public-export JSON is **not** in the repo — `main.rs check_exports` downloads
and refreshes it at runtime into `~/.local/share/kiedas-orbiter/data/export/`, and
that directory is what both the app and this audit read. The audit therefore
reflects the export snapshot currently on this machine; a newer DE export could
change the result. The repo-bundled inputs (`src-tauri/data/assets/data/*.json`,
`src-tauri/data/assets/wfcd/wfcd-combined.json`) are read from the working tree.

## Scope

Audited: the catalogs the app builds from export data alone, i.e. the ones every
user sees regardless of what they own — the Inventory screen tabs, the Mods
screen catalog, and the four Cosmetics screen catalogs. `parseInventory()` is
invoked with an empty raw inventory so only those ownership-independent catalogs
are produced, and each list is checked with the exact resolver its screen uses.

**Not audited, and why:**

- **Owned-item cards.** Items only present because an account owns them cannot be
  enumerated without that account's inventory. Their images come from the same
  export tables, so gaps there are unlikely but not proven absent.
- **Relic catalog (Relics screen).** `Relics.jsx` builds unowned relic cards with
  `image: null` deliberately (Relics.jsx:80) and renders them without an `<img>`.
  That is intended behaviour, not a data gap, so listing every relic here would
  be noise.
- **Worldstate-driven cards** (Dashboard fissures, invasions, Baro/Darvo/Nightwave
  rewards, sorties). Their item lists come from the live worldstate feed, so the
  set of items shown changes hourly and cannot be enumerated statically.
- **Collectibles screen** (fragments, series, markers) and Riven cards, which draw
  from bundled UI art and per-riven weapon lookups rather than these item maps.
