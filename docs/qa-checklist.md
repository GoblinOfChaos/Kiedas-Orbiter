# Kieda's Orbiter — QA / Audit Checklist

This is a checklist of EXPECTED BEHAVIOR to verify against the app's actual code and (where noted) live game data — it is not a bug report. Every line is a testable assertion; check it off once you've confirmed it holds. Lines marked "needs live verification" cannot be confirmed from source code alone and require running the app against real game state/inventory.

Generated by reading every file under `src/screens/*.jsx`, `src/components/overlays/*.jsx`, and shared card/UI components under `src/components/*.jsx`.

## Part 1: Bug-Class Taxonomy

A reference list of reusable bug classes to specifically watch for while working the checklist in Part 2. Each concrete bug found and fixed during the tonight's session is filed under the class it belongs to, for calibration — these are examples of the pattern, not open items.

### 1. Missing interaction handler on a "looks clickable" element
A card, row, or icon is styled identically to its siblings (hover states, cursor-pointer, border-highlight) but is missing the `onClick`/`onChange` handler that makes its siblings actually do something. Most likely where a component has a **bespoke JSX branch** for one special-case item type (e.g. an aggregate/summary card, a locked/veiled card, an empty-state card) that was copy-pasted from the generic branch and lost the handler in the process.
*Example: Inventory.jsx Ayatan sculpture card was missing `onClick={() => toggle(item.unique_name)}`.*

### 2. Boolean "owned" field vs numeric "quantity" field used in the wrong branch
Non-stackable items (ships, warframes, some cosmetics) are tracked with an `owned: boolean`. Stackable items (mods, resources, relics) are tracked with a `quantity`/`count` number. A display branch written for one item type but reused/copy-pasted for the other silently shows "Unowned" or "0" even when the item is actually owned, because it read the wrong field.
*Example: Inventory.jsx Landing Craft "Unowned" label read `quantity` (always undefined/0 for ships) instead of `owned`.*

### 3. Double-counted totals from overlapping source arrays
A total/count is built by summing or `.length`-ing across two or more source arrays (e.g. `warframes` + `all`, or two inventory categories) that can legitimately contain the same `unique_name` in both. Without de-duplication (e.g. via a `Set` or a single canonical source), the displayed count is inflated.
*Example: inventoryParser.js ownership-count map double-counted an item appearing in two source arrays.*

### 4. Case-sensitivity / exact-string-match bugs in generated lookup keys
A lookup key is built via string transforms (`.toUpperCase()`, `.replace()`, template literals) in one place and compared against a key built with different casing/transform rules elsewhere. The comparison silently never matches (`Set.has()` returns false, `find()` returns undefined) with no error thrown.
*Example: relicParser.js Set-based evidence check never matched due to a lowercase/uppercase mismatch from a regex replace.*

### 5. Parent-vs-component (or category-vs-subitem) field conflation
A component/sub-item (e.g. a relic reward's specific blueprint piece, a weapon's barrel) displays a count, owned-flag, or name that actually belongs to its parent/category (the whole weapon, the whole relic) rather than to itself specifically.
*Example: relicParser.js badge showed the PARENT item's count instead of the specific component's own count.*
*Example: Foundry OWNED badge conflated "own the blueprint" (a component of the built item) with "own the built item" (the parent).*

### 6. Overly narrow allowlist/filter that silently zeroes out a whole data class
A filter, regex, or allowlist (e.g. matching only names containing "Prime") is used as a proxy for a broader category, and legitimately misses whole subsets of real data (non-Prime items in that era, items with unusual naming). The UI doesn't error — it just shows an empty/zero result that looks like "nothing to report" instead of "the filter is wrong."
*Example: MonitoringContext.jsx "missing X" counter used a Prime-only allowlist that zeroed out an entire relic era's counter.*

### 7. Raw internal/enum code strings leaking into user-facing text
An internal DE/game-data code (`MT_*` mission types, `CT_*` challenge types, `CET_*` calendar event types, faction tags, polarity codes) is rendered directly instead of being passed through the app's existing translation/lookup table, because a new call site was added without threading it through the lookup, or the lookup table doesn't cover that particular code's category.
*Example: AcquisitionDrawer.jsx dumped a raw `MT_TAU_WAR` code into the UI instead of translating it.*

### 8. Missing acquisition/reference data for whole item categories
An entire category of items (e.g. one item type across the whole game) has no curated acquisition-route/wiki data at all, so every item in that category always falls through to the same generic "no verified route" placeholder — which is easy to mistake for "verified: unobtainable" rather than "data not entered yet."
*Example: wikiVerifiedAcquisitions.js had zero acquisition-route data for landing craft ships.*

### 9. External link / wiki resolution hitting the wrong page due to name collisions
A generic "search the wiki for this name" fallback (used when no curated URL exists) can resolve to an unrelated disambiguation page or a same-named-but-different entity, because the fallback doesn't know about real-world naming collisions that a curated URL would have avoided.
*Example: a generic wiki-search fallback for "Nightwave" resolved to the wrong page due to an unhandled disambiguation collision.*

### 10. Race conditions between independent async effects with no ordering guarantee
Two or more `useEffect` hooks (or async functions) each read/write overlapping state, run independently with no explicit sequencing, and can interleave in either order depending on network/timing — causing the "loser" of the race to silently take a wrong branch or leave stale state visible.
*Example: RivenOverlay.jsx had a race between an async platform-info fetch and an auto-install trigger effect.*

### 11. Self-update / version-tracking drift
The app's self-reported version (in `package.json`/`Cargo.toml`/`getVersion()`) isn't kept in lockstep with actual release tags, so update-availability checks are permanently wrong in one direction (always "update available" or always "up to date").
*Example: package.json/Cargo.toml version was never synced to release tags, so the updater always thought a newer version existed.*

### 12. Missing timeouts / silent hangs on network or long-running operations
A `fetch`/`invoke` call with no timeout can hang indefinitely if the remote endpoint stalls, with no user-visible error state, no retry, and no fallback — the UI just looks permanently "loading."
*Example: main.rs's download_appimage_update had no HTTP timeout, so a stalled request hung forever with zero error surfaced.*

### 13. Self-update writing to the wrong file/path
A downloaded update artifact is saved under a filename/path that doesn't match the file the running instance would actually relaunch from, so the "update" silently does nothing even though it reports success.
*Example: main.rs downloaded a self-update to a different filename than the one actually running.*

### 14. Stale cache / duplicate-instance / re-fetch inconsistency
A cached value (price cache, exported game-data cache, locale cache) is displayed without a clear "last updated" indicator, or a manual refresh button doesn't actually invalidate/replace the stale value it claims to refresh. Related: two windows/processes (main window + overlay windows) both holding independent copies of state that can drift out of sync.

### 15. Controlled-input desync between local React state and persisted setting
A settings control (toggle, slider, text field) updates local `useState` optimistically but the corresponding `setSetting`/`invoke` persistence call is separate — if the persistence call fails or the two ever get out of order (e.g. an external `onSettingsChanged` listener firing concurrently), the displayed UI state can diverge from the actually-persisted/actually-applied backend state.

### 16. Off-by-one / boundary errors in generated grids, indices, and rotations
Calendar day-of-month grids, rotation/tier indices, pagination, and "current vs upcoming" list slicing are all prone to off-by-one errors (wrong starting weekday offset, wrong slice boundary, inclusive vs exclusive date comparisons at cycle expiry).

### 17. Mutually non-exclusive classification buckets
A value is classified into one of several buckets (e.g. "positive stat" vs "negative stat", "owned" vs "missing") via independent boolean checks rather than a single exhaustive branch, allowing a value to satisfy more than one bucket's condition and get double-counted or double-rendered.
*Example: RivenOverlay.jsx stat-classification filter let a value land in both the positive and negative bucket.*

### 18. Locale/translation key gaps
A UI string uses `t('some.key')` but the key is missing from one or more locale files, silently falling back to the raw key string or English text in a non-English UI, rather than the intended localized string.

### 19. Display-name lookup collisions cross-contaminating unrelated items
Two unrelated real DE items share the same display name (e.g. "Crash Course" the rifle mod vs. "Crash Course" the Somachord track; "Alpha/Beta/Stable Corruptor" as both Gear items and Resources). A lookup map keyed purely by lowercased display name (`nameToImage`, drop-table indexes, acquisition-text indexes) has no way to disambiguate, so whichever item is processed last silently overwrites the map entry — the other item then renders the wrong icon, drop table, or acquisition text. A `uniqueName`-keyed lookup is always safe (paths are inherently unique); a name-only lookup never is once two colliding items exist. Found via a dedicated collision-detection pass over the full item dataset (420 total name collisions found, 29 spanning different top-level categories — the dangerous kind).
*Example: `warframeItemsTransform.js`'s `nameToImage` build silently let a later item's icon overwrite an earlier same-named item's icon; fixed by dropping ambiguous name-only keys on detected conflict rather than picking one arbitrarily. Also: the "Omni" gear tool's wfcd drop table was polluted with unrelated "Omni Forma"/"Omni Ammo Box" entries matched by name-prefix substring, not real item identity.*
